# Phase 18 — QA & Release Readiness

Not a redesign, and not the same pass as Phase 12. `validate.js` walks the
journeys on the source; this audits **what is actually uploaded** — `dist/`,
with its inlined CSS and JavaScript and its external images — because that is
what a visitor gets, and the two can differ.

It is a command: `node tools/qa.js`, after `node build.js`.

## 3. Two findings that were the harness lying

Both are recorded rather than quietly deleted, because a test that reports a
false pass — or a false failure — is worse than no test, and this is the second
phase running to catch one.

**The contrast checker read a tag as 1.00:1.** It compared the text colour to
the element's own background *ignoring alpha*: accent text on accent-at-14%
looks identical if you never composite the layer over what is behind it. Fixed
to composite every semi-transparent layer down to the first opaque one. The
real ratio was never in question; the measurement was.

**The disclosure checker reported the scope facts visible while closed.** It
measured the child element, which keeps a bounding box under
`content-visibility: hidden` while painting nothing. The `<details>` itself was
44px tall — exactly its summary — so the state was correct all along.

That one nearly cost more than a false alarm: it prompted a CSS "fix" scoping
the layout to `[open]`, which was **reverted**, because a fix for a defect that
does not exist is a lie in the codebase. The check now measures the element
that actually reserves space.

## 6. What the harness gained after Phase 18

Phase 18 wrote the harness. Four checks were added afterwards, each because
something real got past it. They are recorded here rather than folded into §1,
because the useful thing about a check is the failure that caused it.

| Added | Check | The failure it exists for |
| --- | --- | --- |
| 4 Sep | **Showpiece budget** (§7 in `qa.js`) | Weight, format, poster and `preload` on the hero film — and a 390px load that must request **no video at all** |
| 4 Sep | **Width parity** (§8) | Eight of thirteen package CTAs were `display:none` on phones. Every existing check counted links at one width, so nothing saw it |
| 4 Sep | **`apple-touch-icon`** (§2) | Safari ignores SVG here, and ignores a `data:` URI here, both silently. Three assertions: the link exists on every shipped page, is not inlined, and points at a file that shipped |
| 4 Sep | **Transfer budget** (§9) | Nothing counted what a page actually costs a visitor |

### The transfer budget, and the number it found

`qa.js` capped the HTML at 600KB; `docs/53` caps the showpiece at 2MB. Between
those sat the twelve brand-board panels, uncounted. Measured properly, the
homepage costs a reader who scrolls it **918KB**, excluding the film:

| | Phone (390) | Desktop (1440) |
| --- | ---: | ---: |
| First screen | 510KB | 510KB |
| Full scroll | 918KB | 918KB |
| Showpiece | — (never requested) | +720KB |

Every other page is one file and nothing else: 251–398KB.

**The budget is 1MB per page, excluding the showpiece.** The film keeps its own
number in `docs/53` §2 — counting it twice would let two budgets disagree about
one file. 11% of headroom is deliberate: it is about one more brand-board
panel, which is the size of decision that should be made on purpose.

### A note on how this was measured, because the first attempt lied

The first draft scrolled to `document.body.scrollHeight` in one jump and
reported the homepage at 510KB. That is wrong by 408KB. A lazy image loads when
it enters the viewport, and a page that scrolls past twelve of them in a single
frame never puts any of them there — so the check measured a page with no
images and reported a pass.

This is the third time on this project that a harness has produced a confident
number that was not true (see §3, and the hero screenshots in `docs/54`). The
pattern is the same each time: **the measurement succeeded, so nothing looked
wrong.** A check that cannot fail loudly is worth less than no check, because
it also removes the suspicion that would have found the problem.

## 7. axe-core — a third harness, 4 September 2026

`validate.js` and `qa.js` are both **our opinions about our own work**, written
by whoever wrote the markup. That is precisely the blind spot an accessibility
check should not have. `tools/a11y.js` runs axe-core, an engine nobody on this
project wrote, over the site as deployed.

**What it covers, and why each dimension is there:**

| Dimension | Because |
| --- | --- |
| Every shipped page | 7 pages |
| 390 and 1440 | A rule that hides things on phones is how eight package CTAs disappeared once already (`docs/55` §3) |
| English and Arabic | Arabic swaps `dir`, the fonts and every visible string — and contrast is computed on what is actually painted |
| The mobile drawer, **open** | A dialog is most dangerous when it is the thing on screen, and it is shut on load, so no other pass has ever seen it |

WCAG 2.0 and 2.1, A and AA. Not axe's `best-practice` tag: those are its house
style rather than the standard, and a harness that mixes opinions into failures
teaches people to skim it.

### Result: zero violations, and one exception that had to be argued

The only rule axe broke was `color-contrast` on `.c-footer__mark` — the 176px
"PIXORA" watermark, `#434343` on `#141414`, a ratio of **1.86** where AA wants
3.

**It is kept.** WCAG 1.4.3 exempts text that is pure decoration, and this is
that: the brand name already appears in the footer twice as real text — the
logo lockup and the copyright line — and again in the header. A reader who
cannot make out the watermark loses nothing. Raising it to 3:1 would turn a
texture into a headline and make the footer say the name a fourth time, loudest.

**The exception is conditional, and the condition is re-checked on every run.**
The element must still be `aria-hidden`, and the footer must still carry the
brand name as text that is not. The day the watermark becomes the only place
the name appears it stops being decoration, and the exception lapses by itself
rather than outliving its reason. Verified by removing the `aria-hidden` and
watching the check go red on exactly the page that was edited.

### The guard's own first version was wrong, in the usual direction

It looked for an *element* in the footer whose text contained "Pixora". There
isn't one: the copyright line reads "© 2026 Pixora." out of three nodes — a
literal, a `<span>` holding the year, and another literal. So the guard found
the name nowhere, revoked the exception, and reported a failure on a page that
was fine. It now walks text nodes, which is what a reader does.

**Note the direction of that error.** It failed *loudly*, on a page that was
correct — which is the safe way for a check to be wrong, and the opposite of
the transfer budget in §6, which passed silently on a measurement it had not
made. Given the choice, build the one that shouts.

### What this does not close

Automated rules catch roughly a third to a half of real accessibility defects.
axe cannot tell you that alt text is wrong, that a heading is a lie, that focus
order is confusing, or that a page is incomprehensible read aloud. **§4's
screen-reader pass is still outstanding**, and `a11y.js` prints that line under
every green run so that nobody quotes the green as if it were the pass.

## 8. Paper — 4 September 2026

**`/pricing` printed as a blank sheet with one yellow X.**

Every browser prints with *background graphics* off by default. This is a dark
site: with the grounds gone, `--color-text-primary` is white ink on white
paper. The only mark that survived was the accent letter of the logo, because
it is the one thing on the page dark enough to see against white.

That matters here more than it would on most sites. The pricing page is the one
page a buyer saves to PDF and forwards to whoever signs, and this business
converts by forwarding things. A blank quote is worse than no quote.

### The fix is nine tokens, not a second stylesheet

Every colour on this site resolves through a custom property, so print does not
restate a single component rule: `src/styles/07-print.css` swaps the palette at
`:root` and the whole cascade follows. **Paper is a light theme that already
existed and had never been switched on.** `print` is a new last layer in
`main.css`'s cascade contract, so it wins without `!important`.

The rest of the file is about what paper is, not what colour it is:

| | |
| --- | --- |
| **Hidden** | Navigation a reader cannot tap, the hero film, the contact form, every WhatsApp button, the orbit and the footer watermark |
| **Forced open** | The service accordion and every "show all N features" disclosure — a printed page has no interaction, so anything a reader would have clicked is either printed open or lost |
| **Also hidden, consequently** | The disclosure toggles themselves. "Show all 10 features" sitting directly under all ten of them is worse than no control at all |
| **Page breaks** | `break-inside: avoid` on packages and cards. A package split across sheets puts the price on one page and what it buys on the next |
| **Ink** | Images capped at 8cm, brand boards to two columns. Twelve full-bleed panels would use most of a cartridge |
| **The ribbon** | "Most requested" is white-on-accent on screen, which inverts to black-on-black. It becomes an outlined label instead |

Verified in both languages: Arabic prints right-to-left correctly, and with
background graphics *on* as well as off.

### The check, and what it found when switched off

`qa.js` §10 emulates print media, strips background painting the way the print
dialog does, and measures every visible leaf text element's computed colour
against white — skipping anything the print stylesheet hides, since being
invisible on paper on purpose is half of what that file does.

With `07-print.css` removed, it reports **669 elements at 1:1 on the homepage**
and 56 on the story page. With it, zero.

This is the same shape as §6 and §7: a defect that is invisible on screen,
in a place nobody had looked, found by asking the question rather than by
noticing something. Three for three, the pattern holds — **the site being
correct where you are looking says nothing about where you are not.**

## 9. The accessibility statement, and the drift it caused

`/accessibility` ships 4 September 2026 — bilingual, in the footer beside
Privacy and Terms. It states what was measured, declares the one exception
(`.c-footer__mark` at 1.86:1, §7), and then says the part most statements
leave out: **no screen reader has been used on this site by a person, only one
browser engine has been tested, and no disabled person has been asked.**

Writing it introduced a defect, which is the interesting part.

**The page arrived with Arabic-Indic digits in it** — `٤٤ × ٤٤`, `١٫٨٦`. The
site settled on Western numerals everywhere months ago, in both languages
(`docs/47` §2, `docs/49` §7), and recorded that as *confirmed*. Nothing kept it
confirmed. The bilingual checks count strings and compare parity; both
languages were present and balanced, so every harness passed a page that
contradicted a decision the project had deliberately made.

`qa.js` now counts Arabic-Indic digits and fails on any. **Two wrong versions
of that check came first, and both passed the very page they were written to
catch:**

1. `innerText` — which is rendering-aware. Only one language is displayed at a
   time; the other is `display: none`. On an English-default page it never saw
   the Arabic at all.
2. `textContent` on childless elements — but the sentence carrying the digits
   also carried a `<strong>`, so its span had a child and was skipped.

The third version walks text nodes. That is now the third time on this project
that walking text rather than elements has been the answer — the footer
watermark guard in §7 failed the same way, and for the same reason.

**The general lesson is not about digits.** A decision recorded as "confirmed"
in a document decays the moment someone writes a new page, because a document
cannot fail a build. The check is what makes the decision survive its author's
memory — and a check that passes must be shown to fail first, or it is a
comfort rather than a control.

## 10. The server configuration — 5 September 2026

**`.htaccess` was the one artifact no check touched.** The local server that
serves `dist/` sends no headers of its own, so every rule in that file — the
CSP, the security headers, HSTS, the clean-URL rewrite, the 404 — was
unverified until it was on a real host. `docs/58` T6 already recorded that the
site "looks perfect without it"; nothing recorded that it also looks perfect
with a *wrong* one.

**The catastrophic case is the CSP.** Every page inlines its own module and the
policy names each inline script by sha256. One wrong hash and that page's
JavaScript is refused in production — no accordion, no language toggle, no
package pre-fill — while locally, with no CSP header at all, everything works.
There is no partial version of that failure and no way to notice it before a
visitor does.

`qa.js` §11 now recomputes the hashes from the shipped bytes and matches them
both ways: every inline script must be named, and every name must match a
script. It also asserts the `ErrorDocument` target ships, the extensionless
rewrite is present, HSTS agrees with `site.config.json` in both directions, and
the policy allows the analytics origin exactly when analytics is on.

**Result: the policy was already correct** — four hashes, four distinct inline
scripts, nothing stale. The gap was never the output, it was that nothing
re-checked it.

### The first version of this check reported 24 blocked scripts

It read the policy with `/script-src[^;"]*​/` against the whole file. That
matched a **comment** higher up that mentions "script-src", so it was comparing
against an empty hash list and every script looked missing. Had that been
believed, it would have been reported as a production outage that did not
exist.

Two habits saved it, and both are cheap: **anchor on the directive line rather
than on a word that also appears in prose**, and **be more suspicious of a
check that reports catastrophe than of one that reports nothing** — the second
is the one worth keeping, because the instinct runs the other way.

The negative tests then had a failure of their own: dropping a hash from the
policy produced no finding, which looked like a hole in the check and was
actually a `sed` that required a trailing space where the file has a
semicolon. The edit had silently done nothing. **A negative test that does not
modify what it thinks it modified passes for the same reason a broken check
does.** Re-run properly, all four fire:

| Broken deliberately | Result |
| --- | --- |
| A page's inline script edited, policy unchanged | HIGH, naming the page |
| A hash removed from the policy | HIGH on all seven pages carrying that script |
| `ErrorDocument` pointed at a file that did not ship | HIGH |
| A hash added that matches nothing | MED |

### And one more hole, closed with it

Adding a page needs four registrations: `site.config.json`, `SHIP`, `build.js`
and the footer link. **Miss `SHIP` and the page is built, indexed, canonicalised
and listed in the sitemap — and left out of the archive**, so the URL the
sitemap advertises 404s on the server while `dist/` looks perfect. The
accessibility page needed all four by hand two days ago and nothing would have
caught the omission. §11 now asserts both directions: every indexed page ships,
and every shipped page was built.

## 11. The accessibility tree, read as a listener — 5 September 2026

`docs/62` B6 is a screen-reader pass by a person, and it is still open. But
preparing the brief for it turned out to be findable work rather than only
scheduling work: **a screen reader announces the accessibility tree, and the
tree can be dumped.**

Every interactive element on the homepage, in both languages, printed with the
name it actually announces. Three defects, all of which **passed every
automated check on this project** — axe included — because in each case the
element *had* an accessible name and the name was simply useless:

| Announced as | Fixed to |
| --- | --- |
| `button "Copy"` | `button "Copy the email address"` |
| `link "See what it covers"` × 5, identical, one per service | `link "See what it covers in Branding & Design"`, and four more |
| `link "Website"` | `link "Founder's portfolio"` |

**The near-miss is the part worth keeping.** The obvious fix for the first was
a visually-hidden span inside the button. That button carries `data-i18n`, and
the runtime does `el.textContent = t(...)` — which erases children. The fix
would have looked correct in the markup, passed review, and done nothing in a
browser. It uses `aria-label` via the site's existing `data-i18n-label`
mechanism instead.

Reading the runtime before writing the fix is what caught it, and this is the
fifth time on this project that a check or a fix has looked right while
measuring or changing nothing.

**What this does not close.** The tree says what is announced; it cannot say
whether the announcement makes sense, whether alt text describing brand
artwork conveys anything, or whether a "Ask about Starter" button should warn
that it opens WhatsApp. `docs/67` §2 is that list, and it still needs ears.

## 12. A CSS rule that had never fired — 5 September 2026

Arabic typography was checked against sourced 2026 practice, expecting to find
nothing: letter-spacing is zero on Arabic (proved by finding 142 Latin elements
first, so the probe was known to work), and body leading is 1.75, which is
right for Arabic.

Then the headings. `src/styles/03-base.css` carried a rule whose comment said
Arabic headings take `--leading-heading` — 1.18, deliberately above the Latin
display value of 1.02, because Arabic needs the room. It selected
`.t-display-xl, .t-display-l, .t-h1 … .t-h4`.

**Not one of those classes appears anywhere in the markup.** The site styles
headings through component classes — `.c-hero__headline`, `.c-detail__headline`
— so the rule matched nothing and had never once fired. Every Arabic heading
fell through to the generic `:lang(ar)` rule above it and took
`--leading-relaxed`: 1.75. Body leading, on a 76px display headline.

### What it cost

Measured on the built site at 1440×900, Arabic:

| | Before | After |
| --- | ---: | ---: |
| Hero headline height | **532px** | 359px |
| Hero CTA bottom edge | **884px** | 711px |
| Fold | 900px | 900px |

At 884px the primary call to action on the Arabic homepage was two pixels above
a 900px fold in a browser with no chrome, and below it in every real one. On a
390×844 phone it sat at 701px and now sits at 528px. The h1 was four lines of
near-detached words where the English is two.

Every page moved: `/pricing`, `/about`, `/privacy`, `/terms` headlines 218px →
147px, `/story` and `/accessibility` 109px → 74px. English is byte-identical in
layout — 19,873px document height before and after, on the homepage.

### The first fix changed nothing, and that is the finding

Adding `h1, h2, h3, h4` to the selector list produced **532px before and 532px
after**. The reason is the bilingual markup: every string is a pair of spans and
it is the *span* that carries `lang="ar"`, so the span matches the generic
`:lang(ar)` rule and takes body leading no matter what the heading around it is
told. The text is in the span, so the span is what has to be told. Hence the
`:lang(ar) :is(h1, h2, h3, h4) *` half of the selector.

That inheritance was then checked for collateral: zero visible Latin-only
elements sit inside a heading on any page in Arabic mode, so nothing Latin
picked up the Arabic face.

**This is the sixth time on this project that a check or a fix has looked right
while measuring or changing nothing** — and the first where the thing that had
never fired was shipped production CSS rather than a harness. The harnesses
could not have caught it: `validate`, `qa` and `a11y` all pass at 532px, because
a headline being too tall is not a violation of anything they measure.

**The rule is now keyed on the elements**, so a component added tomorrow
inherits the intent without anyone remembering the rule exists. The `.t-*`
classes stay for `/styleguide`, which does use them.

## 13. A twelfth section, and what it found on the first run — 5 September 2026

§12 ended with "the harnesses could not have caught it." That was true, and it
was the wrong place to stop. `qa.js` §12 now catches it.

### What the check turns on

A dead selector is not automatically a defect. The distinction:

| | |
| --- | --- |
| `.t-small { font-size: … }` | a **definition**. Nobody used it. Inert |
| `:lang(ar) .t-h1 { … }` | an **assertion** — *under this condition, change that thing*. Matching nothing means the condition it was written for is silently unhandled |

A dead selector is HIGH, and fails the build, when both halves of it exist and
only the combination does not: **the condition matches something, and every
class it targets appears in the markup somewhere else.** That is exactly the
shape of the heading rule — `:lang(ar)` matched, `.t-h1` existed on
`/styleguide`, and no heading anywhere carried both. Everything else dead is
one LOW inventory line.

Aliveness is judged on the **shipped** pages only, and that detail is the whole
check. `/styleguide` is built into `dist/` and deployed to nobody, and it demos
the type scale with Arabic samples — so `:lang(ar) .t-h3` matches there and
nowhere else. **Judged across both sets, the bug this section exists to catch
reads as live, and the first version of the check passed it.** A rule that
applies only on a page no visitor can open has, for every visitor, never
applied.

Where a dead rule is deliberate, `qa:allow-dead` in the comment above it
exempts it — and the comment is where the reason has to be written. Two rules
use it, both RTL rules for components that exist only on `/styleguide`.

### The first run found a live defect, and it was not the one being looked for

Before any selector was tested, the comment-balance pass reported
`service-detail.css:557`: **a `*/` that closes no comment.**

A comment describing the phone CTA decision closed early, at
`they come back. */`. The twelve lines of prose after it — the *"REVERSED 4
September 2026"* note — were being parsed as CSS. A browser reads that prose as
a selector prelude, consumes it and the block that follows, and discards both.
The block that followed was:

```css
.c-tier__cta {
  display: inline-flex;
  margin-block-start: auto;
  inline-size: 100%;
}
```

Confirmed in the browser rather than reasoned about: `document.styleSheets`
contained **zero** rules matching `.c-tier__cta`, and the computed
`margin-block-start` was `0px` where the source says `auto`.

**What it cost.** `margin-block-start: auto` is what pushes each package button
to the bottom of its card so that three cards of different heights present
their buttons on one line. Measured on the homepage at 1440×900, before:

| Service grid | Button top spread | Dead space under each button |
| --- | ---: | --- |
| 1 | 102px | 143, 41, 75px |
| 2 | **252px** | 293, 168, 41px |
| 3 | 135px | 176, 74, 41px |
| 4 | 107px | 148, 99, 41px |

After: **0px spread and a uniform 41px on all four.** The three buttons that
present a choice were floating at three different heights, on the homepage, in
production — a quarter of a screen apart on the second service.

The irony is exact. The swallowed comment is the one recording that these
buttons had been wrongly hidden on phones and were restored; the note
explaining the fix broke the rule that implements it.

### And a second dead `.t-*` rule, removed

`03-base.css` carried one more of the same kind:

```css
:lang(ar) :is(.t-price, .t-price-sm, .t-stat) { letter-spacing: … }
```

**Deleted rather than re-keyed, because its intent is already met.** Measured
on `/pricing` in Arabic: every price already renders at `letter-spacing:
normal`, and the parts order correctly right-to-left — *"يبدأ من 490 دولار"*
puts the amount before the currency, as Arabic requires. Removing it left every
price box at byte-identical coordinates. Re-keying it would have restated
something already true.

### The inventory it leaves behind

**163 selectors style nothing any visitor can see** — mostly a design system
larger than the site has ordered (`card.css` 33, `disclosure.css` 30,
`04-layout.css` 24), demoed on `/styleguide` and inlined into all eight shipped
pages regardless. Not a defect, and not silently dropped either: it is one LOW
line every run, so pruning stays a choice rather than a discovery.

### Both checks were tested by breaking the code again

The recurring failure on this project is a check that passes while testing
nothing — six instances by §12's count. So neither of these was trusted until
the original faults were reintroduced and both were seen to fail:

- the heading rule reverted to its `.t-*`-only selector → **2 HIGH at
  `03-base.css:238`**, naming the selector;
- the comment terminator put back → **1 HIGH at `service-detail.css:557`**.

The first version of the selector check **passed the reverted heading rule**,
which is how the shipped-pages-only distinction was found. Had it been trusted
on its clean first run, this section would have recorded a check that could not
detect the bug it was written for — a seventh instance.

## 14. E6, and the defect that was hiding inside it — 5 September 2026

`docs/62` E6 was a housekeeping item: **163 selectors style nothing a visitor
can see.** It turned out to contain an accessibility defect on every page.

### 125 lists that were not lists

`01-reset.css` carries the opt-in idiom:

```css
ul[role="list"], ol[role="list"] { list-style: none; padding: 0; }
```

It exists because **removing a list's marker removes its list semantics in
Safari**, which is what VoiceOver reads. The idiom's whole point is that a list
which strips its bullets must say `role="list"` to stay a list.

That rule was in E6's dead list. It matched nothing — and the reason was not
that the rule was wrong:

| | |
| --- | --- |
| Lists across the eight shipped pages | 164 |
| With their marker removed by CSS | **125** |
| Carrying `role="list"` | **0** |

Twenty-plus component rules set `list-style: none` and no list anywhere opted
in. On VoiceOver — the device `docs/67` names as most representative for this
market — the navigation, the footer, every package's feature list, the service
lists and the add-ons were announced as loose runs of text rather than *"list,
5 items"*, with no item count and degraded item-by-item navigation.

**axe-core reports zero violations here**, on every page, at two widths, in both
languages. It is a Safari behaviour rather than a rule violation, so no
automated check on this project could see it. It took a *dead CSS rule* to
point at it.

`role="list"` is now on all 125, at every source of truth — `index.html` (the
shell the other pages are built from), `build-pricing.js` for the generated
tier lists, and `navigation.js` for the drawer sub-lists it creates at runtime.
The 39 lists that keep their markers were left alone. **Measured before and
after: document height identical on all eight pages, in both languages, at
1440×900 and 390×844.** Nothing moved; only the announcement changed.

`qa.js` now fails the build on any list that removes its marker without the
role — verified by removing one and watching it fail, after a first attempt at
that negative test edited nothing because the attributes were not adjacent in
the built file. Seventh instance of this project's recurring pattern, caught
because the edit was asserted rather than assumed.

### The pruning itself

**`card.css` and `disclosure.css` had zero live rules between them** across all
eight shipped pages — 10.2KB of CSS inlined into every page so that one
undeployed page could demo it. They now load from `src/styles/showroom.css`,
which only `/styleguide` links.

Deleted outright, because nothing uses them and nothing demos them:
`.c-hero__action-chevron`, `.c-tiers--pair > :last-child`, `.c-services__foot`
(2 rules), `.c-choice__input[type="radio"]` (2 rules). `.c-scrim` left the print
hide-list — it is a component that exists in no markup, no script and no
specimen. And `.c-page__headline` in the print stylesheet was a name that never
existed; the element is `.c-page__title`, and the rule only ever worked because
a bare `h1` sat beside it in the same selector list.

`qa.js` §12 now follows the `@import` chain from `main.css` rather than globbing
`src/styles`, so it reports what a visitor downloads and not what
`/styleguide` loads.

### What was deliberately not pruned, and why

Removing **every** dead rule was measured first: it saves ~2.5KB gzipped per
page, about 2%. That number is what decided the rest.

Of the 91 remaining, **35 rules (2.7KB) are used by nobody at all** — the `.l-*`
layout modifiers and the `.u-*` spacing and visibility utilities — and 53
(6.2KB) are exercised only by `/styleguide` from inside files whose other half
is live.

They stay, for two reasons. `docs/00-design-system.md` publishes several of
them as API, so they are a promise rather than an accident. And **X09 is
Design System Refinement** — pruning the vocabulary immediately before the
phase that decides the system's shape is the wrong order. Splitting
`04-layout.css` down the middle by current usage would also cost more in
readability than the ~0.5KB gzipped it would save: `.l-section--deep` belongs
next to `.l-section`, not in another file.

So E6 closes as a decision rather than an empty list. The count is printed on
every run, so what remains stays a choice.

## 15. E4, and a decision AD-06 framed wrongly — 5 September 2026

`docs/62` E4 is *"split-bundle option for repeat visits, alongside the single
file"*, and AD-06's revisit trigger reads **"when repeat-visit traffic matters
more than first paint."** That framing turned out to be the wrong question, and
measuring it is what showed why.

### What is actually in a page

Every shipped page carries a byte-identical copy of the same CSS. On the
homepage:

| part | raw | gzipped |
| --- | ---: | ---: |
| whole page | 491.8KB | 134.8KB |
| inline CSS | 185.4KB | 77.9KB |
| **of which `@font-face`** | **83.1KB** | **61.5KB** |
| CSS without the fonts | 102.3KB | 16.2KB |
| inline JS | 42.1KB | 13.0KB |
| the HTML itself | 264.2KB | 42.7KB |

**Fonts are 46% of the gzipped page**, and the same 46% on all eight.

### The intent that inlining silently defeated

`00-fonts.css` says, in its own header:

> *"`unicode-range` lets the browser skip any subset the page never uses — an
> English page never downloads the Arabic file, and vice versa."*

**A data URI is not a download.** There is nothing for the browser to skip: the
bytes arrived inside the HTML whether or not a single Arabic glyph is ever
rendered. Every English visitor was paying for the 30.9KB Cairo face to render
text they cannot see, on every page.

Verified in a browser against a linked build, rather than argued:

| | files fetched | bytes |
| --- | ---: | --- |
| English | **4** | 30.7KB — Poppins only |
| After switching to Arabic | 5 | 60.9KB — Cairo arrives on demand |

This is the same shape as §12 and §14: a mechanism written with a stated intent
that the pipeline quietly cancels. Third instance, and the first where the
canceller was the build rather than a selector.

### The measurement

`site.config.json` `build.fonts` now chooses. Gzipped, every shipped page:

| page | `inline` | `linked` | |
| --- | ---: | ---: | ---: |
| index | 139,946 | **75,129** | −46% |
| pricing | 113,123 | **48,456** | −57% |
| story | 107,190 | **42,605** | −60% |
| terms | 106,835 | **42,190** | −61% |
| accessibility | 105,779 | **41,119** | −61% |
| privacy | 104,394 | **39,721** | −62% |
| about | 103,837 | **39,151** | −62% |
| 404 | 99,559 | **35,020** | −65% |

Fonts are 62,344 bytes on disk, fetched once for the whole site. An English
visitor fetches 31,448 of them.

**So it is not a repeat-visit trade at all.** A first-time English visitor
landing on the homepage and reading nothing else:

- `inline` — 139,946 bytes
- `linked` — 75,129 + 31,448 = **106,577 bytes, 24% less**

with no cache involved. The saving is the Arabic font they never see. A
three-page English journey (home → pricing → about) is 356,906 against
**194,184**, 46% less. An Arabic visitor's first page is a wash — 137,473
against 139,946 — and every page after it costs 57–62% less.

### The cost, measured — and it is not a cost

The objection to `linked` is real in principle. Every face is
`font-display: swap`; with the bytes already in the document that swap is
instant and no fallback is ever seen, while linked there is a window where the
page has painted and Poppins has not arrived.

**AD-06's premise is that separate files cost round trips and hurt first
paint.** Measured on a simulated 1.6Mbps / 150ms-RTT connection at 390×844,
gzip on — because serving uncompressed would penalise whichever mode
compresses better, which is the mode under test — five runs each, median:

| | `inline` | `linked` | |
| --- | ---: | ---: | ---: |
| index.html, first contentful paint | 648ms | **440ms** | −32% |
| about.html | 640ms | **456ms** | −29% |

**The premise is inverted here.** The inlined font bytes were themselves in the
render-blocking path: nothing could paint until all 134.8KB of document had
arrived, 61.5KB of which was fonts. Linked, 75KB arrives and paints, and the
faces stream alongside.

And the fallback window is largely closed by something that was already in the
repository. `index.html` has preloaded *"the two faces the first screen needs"*
since it was written — and the build **stripped those tags**, correctly, with
the comment *"font preloads are pointless once the bytes are in the
document."* In linked mode they are kept and repointed instead. Measured:
the two preloaded faces are requested at **182ms**, against ~1000ms for the
faces that wait for layout to prove they are needed. They arrive well before
the 440ms paint. Cairo is deliberately not preloaded — skipping it for English
readers is the whole point. `404.html` gained the same two tags; it was the one
page that never had them.

So `linked` is now the default. It wins on bytes, on first paint, and on the
Arabic face English readers never see, and the one thing it was supposed to
cost is answered by preloads. `inline` remains available and tested.

`qa.js` §13 fails the build if a linked page references a face the zip does not
carry — verified by deleting one and watching all eight pages fail — and also
if the two modes and the artefact disagree in either direction. The fonts ship
in `pixora-site.zip` under `assets/fonts/`, confirmed in the archive.

Both modes were run through all three harnesses: `validate: 0 · qa: 0 high ·
a11y: 0`. Requests per page go from 2 to 6 on the homepage and 1 to 5
elsewhere; page weight 514KB → 423KB and 401KB → 310KB.
